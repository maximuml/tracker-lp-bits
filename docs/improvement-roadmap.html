План улучшения tracker-lp-bits

Подробный поэтапный roadmap модернизации приватного BitTorrent-трекера на базе NexusPHP / Laravel 13.

1. Назначение документа

Этот документ описывает поэтапный план дальнейшего улучшения tracker-lp-bits после завершённых спринтов модернизации. План ориентирован на снижение эксплуатационных и security-рисков, упрощение архитектуры, повышение достоверности CI и постепенное сокращение legacy-поверхности без нарушения совместимости с существующими URL, BitTorrent-клиентами и пользовательскими сценариями.

План не задаёт календарные сроки. Работы следует выполнять небольшими изолированными pull request, каждый из которых имеет измеримый результат, тесты и понятный rollback.

2. Исходное состояние

2.1. Сильные стороны

  • Laravel 13, PHP 8.4/8.5, Filament 5, MySQL, Redis и MeiliSearch.
  • PHPStan level 8 и Laravel Pint выполняются в CI.
  • Unit, Feature, Architecture, Docker smoke, accessibility и performance workflows.
  • Изолированные тестовые базы и DestructiveEnvironmentGuard.
  • Stateless announce pipeline с AnnounceContext.
  • Query budgets для ключевых страниц и tracker endpoint.
  • CodeQL, gitleaks, Semgrep, Trivy, dependency review и SBOM generation.
  • Production image запускается от www-data с read-only root filesystem.
  • Архитектурные ratchet-тесты ограничивают рост legacy-паттернов.
  • Concrete controllers имеют соответствующие controller tests, хотя глубина HTTP-покрытия различается.

2.3. Основные проблемы

  1. CI содержит fail-open проверки, которые могут завершиться успешно при ошибке анализа.
  2. Coverage gate повторно запускает тесты и пропускает ошибку парсинга результата.
  3. Разделённые GET/POST routes часто ведут в один controller action, совмещающий чтение и mutation.
  4. Controllers и services активно используют app() и скрытые зависимости.
  5. Крупные repositories/services объединяют несколько use cases.
  6. Значительная доля controller tests вызывает методы напрямую и не проверяет весь HTTP pipeline.
  7. Legacy Blade содержит много PHP-логики, raw output, layout tables и inline JavaScript.
  8. Production Compose не проверяется полноценным cold-start тестом на новых volumes.
  9. Observability-код сконцентрирован в крупных controllers и частично раскрывает технические детали.
  10. Документация и отдельные ratchet-комментарии местами отстают от фактического состояния кода.

3. Общие принципы выполнения

3.1. Размер изменений

  • Один PR должен решать одну архитектурную или функциональную задачу.
  • Нельзя объединять массовый рефакторинг с изменением пользовательского поведения.
  • Сначала фиксируется текущее поведение тестом, затем выполняется рефакторинг.
  • Legacy URL и .php aliases сохраняются до отдельного решения об их удалении.
  • Ratchet baseline можно только уменьшать. Исключение требует отдельного архитектурного решения.

3.2. Обязательные проверки каждого PR

Минимальный набор:

make test-lint
make test-unit
make test-feature
make test-architecture
npm run build

Для изменений tracker, legacy pages, Docker или MeiliSearch дополнительно:

make test
docker compose config
docker compose exec -T php php artisan route:cache
docker compose exec -T php php artisan view:cache

Для security-sensitive изменений:

docker compose exec -T php composer audit
npm audit

Для announce/scrape, auth, uploads, comments, usercp и staff pages выполняются соответствующие Docker E2E сценарии из .agents/skills/.

3.3. Definition of Done

Задача считается завершённой, когда:

  • добавлены или обновлены тесты, фиксирующие требуемое поведение;
  • PHPStan, Pint и релевантные suites проходят;
  • нет повышения architecture baseline;
  • новые зависимости не разрешаются через service locator без обоснования;
  • security и authorization проверяются на HTTP-уровне;
  • обновлена существующая документация, если изменились команды или архитектурные решения;
  • проверен rollback или обратная совместимость, если изменение затрагивает данные, маршруты или deployment.

4. Волна 0 — достоверность CI и baseline

P0
Цель

гарантировать, что зелёный CI действительно означает успешное выполнение проверок.

W0-01. Сделать Semgrep обязательным

Работы:

  1. Удалить безусловный || true из основного Semgrep job.
  2. Разделить правила на два набора:
    • blocking: локальные проверенные правила из .semgrep.yml;
    • informational: шумные community rules.
  3. Зафиксировать версию Semgrep вместо установки непредсказуемой последней версии.
  4. Добавить явный artifact или job summary с количеством findings.
  5. Создать baseline только для подтверждённых старых findings; новые findings должны блокировать PR.

Критерии приёмки

  • синтаксическая ошибка Semgrep или невозможность запустить scanner приводит к failed job;
  • новый finding blocking-категории приводит к failed job;
  • существующие принятые findings перечислены явно, а не скрыты общим || true.

W0-02. Вернуть blocking Trivy gate

Работы:

  1. Обновить Trivy action/version до версии без известного бага с rejected CVE.
  2. Удалить continue-on-error с PHP и OpenResty scans.
  3. Проверять CRITICAL,HIGH на каждом PR.
  4. Оставить полный CRITICAL,HIGH,MEDIUM,LOW scan по расписанию.
  5. Каждая запись .trivyignore должна содержать причину и срок пересмотра.
  6. Добавить отдельную проверку, запрещающую бессрочные или неизвестные ignore entries.

Критерии приёмки

  • подтверждённая неисключённая CRITICAL/HIGH vulnerability блокирует PR;
  • scanner failure не считается успехом;
  • scheduled scan публикует SARIF даже при отсутствии blocking findings.

W0-03. Исправить dependency review

Работы:

  1. Проверить доступность dependency graph для целевого GitHub repository.
  2. Если доступно — убрать continue-on-error и блокировать зависимости severity moderate и выше.
  3. Если недоступно — явно помечать job как skipped с причиной и компенсировать Composer/npm audit.
  4. Добавить проверку лицензий для новых production dependencies.

Критерии приёмки

  • новый vulnerable production package не может пройти незамеченным;
  • отключённая GitHub capability отображается как отдельное состояние, а не маскируется зелёным job.

W0-04. Сделать coverage gate fail-closed

Работы:

  1. Удалить повторный запуск Unit suite только ради получения процента.
  2. Читать line coverage из уже созданных Clover XML.
  3. Валидировать наличие и корректность обоих файлов: Unit и Feature.
  4. Считать объединённое project coverage либо использовать отдельные обязательные thresholds.
  5. Убрать || true и успешный выход при невозможности распарсить coverage.
  6. Сделать Codecov patch status обязательным, если token и GitHub integration доступны.
  7. Сохранить начальный floor 35%, затем повышать только после стабилизации.

Критерии приёмки

  • отсутствующий или повреждённый report ломает job;
  • project coverage ниже floor ломает job;
  • patch coverage ниже 60% ломает PR, кроме явно исключённых generated/migration файлов;
  • coverage suite запускается один раз на тип тестов.

W0-05. Исправить архитектурные ratchets

Работы:

  1. Пересчитать все baseline текущими тестами.
  2. Исправить RepositorySizeTest: удалить entry файла, который не превышает 500 строк, и синхронизировать комментарии с массивом.
  3. Не считать стандартные API PUT+PATCH routes долгом, который обязательно должен дойти до нуля.
  4. Добавить тест, находящий одинаковые URI + controller action, зарегистрированные отдельно для GET и POST.
  5. Добавить отдельный ratchet на app():
    • controllers;
    • services;
    • repositories;
    • прочие namespaces.
  6. Добавить проверку stale baseline entries.
  7. Обновить описание modernisation status и актуальное количество tests/controllers.

Критерии приёмки

  • ratchet отражает архитектурный риск, а не нормальное REST-поведение;
  • ни один baseline не содержит файл вне определяемой категории;
  • одинаковый GET/POST action нельзя добавить без явного allow-list и причины.
Результат волны 0

Все quality/security checks fail-closed. Coverage измеряется воспроизводимо. Baseline соответствует фактическому коду. Последующие волны получают надёжную систему контроля регрессий.

5. Волна 1 — HTTP boundaries и authorization

P0–P1
Зависит от

Волна 0

Цель

отделить rendering/query actions от mutations и проверять безопасность через реальный HTTP pipeline.

W1-01. Инвентаризация legacy routes

Сформировать генерируемый отчёт со столбцами:

  • URI и legacy alias;
  • HTTP method;
  • controller action;
  • middleware;
  • authentication guard;
  • authorization policy/gate;
  • FormRequest;
  • read-only или mutation;
  • Feature test;
  • E2E test.

Распределить routes по доменам:

  1. Auth и registration.
  2. Torrent read paths.
  3. Torrent mutations.
  4. Forum и comments.
  5. Messages и friends.
  6. Usercp и settings.
  7. Bonus/invites/attendance.
  8. Moderation/staff/admin.
  9. Utility, attachments и search.
  10. Tracker protocol.

Критерий приёмки

все зарегистрированные web/legacy/API routes представлены в отчёте, а mutation route без authorization отмечен как blocker.

W1-02. Строгая authorization matrix

Работы:

  1. Заменить ожидания 403 или 404 точными статусами.
  2. Заменить проверку status != 401 проверкой конкретного success/validation результата.
  3. Добавить роли:
    • anonymous;
    • authenticated user;
    • uploader;
    • moderator;
    • administrator/sysop;
    • disabled/banned user.
  4. Проверять и Sanctum abilities, и underlying domain permission.
  5. Добавить object-level authorization для чужих messages, comments, torrents и user data.
  6. Проверять 405 для неправильного HTTP method.

Критерии приёмки

  • каждый API mutation имеет negative и positive authorization test;
  • 401, 403, 404, 405 и 422 не считаются взаимозаменяемыми;
  • тест подтверждает database side effect либо его отсутствие.

W1-03. Разделить GET/POST actions: messages

Работы:

  • GET mailbox/show/create form вынести в query/display actions;
  • POST send/update/delete вынести в command actions;
  • validation перенести в FormRequest;
  • ownership и staff permissions перенести в policies;
  • сохранить legacy redirects и response shape API;
  • добавить HTTP Feature tests и legacy E2E.

Критерии приёмки

  • GET не изменяет messages/read state без явно документированного решения;
  • mutations недоступны через GET;
  • прямой вызов service locator из новых actions отсутствует;
  • legacy и API сценарии дают эквивалентный доменный результат.

W1-04. Разделить GET/POST actions: forum и comments

Работы:

  • разделить list/show/new topic/reply/edit/delete/moderation;
  • использовать route model binding там, где это не ломает legacy aliases;
  • вынести anti-flood в отдельный domain service/policy;
  • унифицировать authorization legacy и API paths;
  • добавить tests для locked topic, deleted post, чужого post и moderator override.

Критерии приёмки

  • каждый mutation имеет отдельный method и FormRequest;
  • policy применяется одинаково для legacy и API;
  • нет GET deletion links, выполняющих удаление без POST/DELETE confirmation.

W1-05. Разделить GET/POST actions: usercp/settings

Работы:

  • отдельные actions для personal/forum/tracker/security preferences;
  • typed DTO для каждой группы настроек;
  • password/passkey операции отделить от обычных preferences;
  • sensitive changes защищать current-password confirmation;
  • сброс caches выполнять через domain event/listener.

Критерии приёмки

  • изменение security settings невозможно без требуемого подтверждения;
  • неизвестные поля не приводят к mass assignment;
  • legacy forms и API используют один application service.

W1-06. Разделить torrent mutations

Область:

  • upload;
  • edit;
  • delete/fast delete;
  • bookmark/thanks;
  • reseed;
  • promotion/state changes;
  • download notice preferences.

Работы:

  • отдельные command services и transaction boundaries;
  • file system operation согласовать с DB transaction через staged file/outbox cleanup;
  • policy на каждый mutation;
  • idempotency для повторной отправки формы, где применимо;
  • audit event для staff mutations.

Критерии приёмки

  • частичная ошибка не оставляет orphan torrent files или неполные DB rows;
  • повторный request не создаёт дубль;
  • все destructive actions имеют точные permission tests.

W1-07. Staff/admin mutations

Работы:

  • инвентаризировать legacy admin endpoints, которые уже редиректятся в Filament;
  • удалить недостижимую реализацию после периода совместимости;
  • оставшиеся mass/bulk operations оформить как jobs с audit trail;
  • добавить dry-run для потенциально массовых операций;
  • ограничить batch size и добавить idempotency key.

Критерии приёмки

  • массовая операция не выполняется синхронно в web request;
  • actor, параметры и результат записываются в activity log;
  • повтор job безопасен.

6. Волна 2 — Dependency Injection и request context

P1
Зависит от

Волна 1 для соответствующего домена

Цель

сделать зависимости явными и уменьшить риск cross-request state leakage.

W2-01. Детализированный ratchet на app()

Работы:

  • зафиксировать baseline по namespace и файлам;
  • запретить новые app() в controllers/services;
  • разрешить container access только в framework adapters/providers/factories;
  • публиковать top-20 файлов по количеству вызовов в CI artifact.

Целевая метрика первой итерации:

  • controllers: снижение минимум на 20%;
  • services: снижение минимум на 20%;
  • отсутствие новых файлов с app() вне allow-list.

W2-02. Constructor injection в критичных flows

Порядок:

  1. Auth/passkey/recovery.
  2. Announce/scrape.
  3. Torrent mutations.
  4. Messages/forum.
  5. Usercp.
  6. Moderation/cleanup.

Правила:

  • не создавать интерфейс для каждого repository автоматически;
  • интерфейсы использовать на внешних границах: clock, network, cache, search, queue, mail, filesystem;
  • Laravel facades допустимы в infrastructure adapters, но не в domain logic;
  • зависимости request scope не должны регистрироваться singleton.

Критерий приёмки

новый или изменённый application service можно создать в unit test без boot полного Laravel container.

W2-03. Убрать side effect из AnnounceRequestDto

Работы:

  • AnnounceRequestDto::fromRequest() не должен вызывать SupportContext::fromRequest();
  • вынести parsing в AnnounceRequestFactory;
  • внедрить ClientIpResolver и user-agent source;
  • оставить DTO immutable и не связанным с глобальным состоянием;
  • добавить IPv4/IPv6/trusted proxy tests.

Критерии приёмки

  • создание DTO не меняет request/global context;
  • parser тестируется без Laravel application;
  • spoofed forwarding headers обрабатываются согласно trusted proxy configuration.

W2-04. Завершить stateless announce response

Работы:

  • проверить lifecycle и registration ResponseBuilder;
  • сделать его immutable либо гарантированно request-scoped;
  • добавить Octane/RoadRunner cross-request tests;
  • проверить повторные started, completed, stopped events;
  • проверить параллельные announces одного пользователя и разных peers;
  • проверить lock expiration и transaction retry при deadlock.

Критерии приёмки

  • response/state одного request не видны следующему request;
  • concurrency tests воспроизводимы и не зависят от случайных sleep;
  • повторный completed event не удваивает accounting.

W2-05. Сократить typed global configuration debt

Работы:

  • сгруппировать оставшиеся Globals usage по доменам;
  • расширять typed config objects небольшими тематическими наборами;
  • запретить передачу необработанного массива settings в domain services;
  • обновлять config caches через единый механизм;
  • добавить schema/default validation для обязательных settings.

Целевая метрика: снижать Globals baseline минимум на 10–15% за волну без создания нового универсального config god object.

7. Волна 3 — тестовая стратегия

P1
Цель

повысить способность тестов обнаруживать реальные regressions, а не только увеличить их количество.

W3-01. Классифицировать существующие tests

Для каждого critical flow отметить:

  • pure unit;
  • service integration;
  • HTTP feature;
  • Docker E2E;
  • concurrency;
  • mutation testing;
  • performance budget.

Удалять дублирующие direct-controller tests можно только после появления более сильного HTTP или service-level теста.

W3-02. HTTP contract tests

Добавить data-driven contract tests для:

  • expected route methods;
  • middleware presence;
  • auth guard;
  • content type;
  • redirects;
  • API response envelope;
  • validation errors;
  • legacy alias parity.

Критерий приёмки

изменение route method, middleware или response contract приводит к понятному точечному падению теста.

W3-03. Concurrency tests

Приоритетные сценарии:

  • announce accounting;
  • seed bonus начисление;
  • attendance claim;
  • bookmark/thanks duplicate submission;
  • invite consumption;
  • torrent delete/edit collision;
  • outbox claim/retry/dead-letter;
  • cleanup jobs overlap.

Требования:

  • использовать отдельную test database;
  • проверять инварианты после завершения параллельных операций;
  • не считать тест пройденным только из-за отсутствия exception.

W3-04. Mutation testing на PR

Работы:

  • вычислять изменённые critical files;
  • запускать Infection только для них на PR;
  • полный scope оставлять на push/nightly;
  • добавить policies, torrent mutations и outbox;
  • после стабилизации поднять MSI до 50, затем рассмотреть 60.

Критерий приёмки

изменение security/validation condition, которое не ловят tests, отображается как escaped mutant и требует решения.

W3-05. Реалистичные fixtures

Работы:

  • добавить builders/scenarios вместо несвязанных factory calls;
  • создать datasets для torrent listing, forum, messages и moderation;
  • query budget tests выполнять на десятках/сотнях связанных records;
  • исключить зависимость tests от фиксированных production-like ID.

Критерий приёмки

N+1 regression обнаруживается на локальном/CI dataset.

W3-06. Увеличение coverage thresholds

После завершения W1–W3:

  1. Зафиксировать стабильное объединённое coverage.
  2. Поднять project floor с 35% до ближайшего безопасного значения.
  3. Далее повышать не более чем небольшими шагами.
  4. Для critical namespaces установить отдельные более высокие thresholds.

Предлагаемые конечные ориентиры:

  • Auth/Tracker/Policies: не менее 80% line coverage плюс mutation testing;
  • application services: не менее 70%;
  • общий project floor: сначала 45%, затем 55% при сохранении качества tests.

Coverage не является самостоятельной целью и не заменяет scenario/authorization/concurrency tests.

9. Волна 5 — SQL и производительность

P2
Цель

контролировать не только количество raw SQL, но и его безопасность и стоимость.

W5-01. Реестр raw SQL

Для каждого raw expression/query хранить:

  • файл и метод;
  • назначение;
  • database compatibility;
  • наличие bindings;
  • ожидаемый индекс;
  • причина невозможности выразить через query builder;
  • owning domain.

Правила:

  • пользовательские значения передаются только bindings;
  • динамические identifiers выбираются из allow-list;
  • string concatenation для пользовательских values запрещена;
  • Install/Upgrade SQL рассматривается отдельно от runtime SQL.

W5-02. EXPLAIN regression tests

Приоритетные queries:

  • torrent listing/search;
  • torrent details relationships;
  • top ten;
  • user search/IP moderation;
  • unread forum/messages;
  • announce peer lookup;
  • outbox pending events;
  • cleanup selection.

Проверять:

  • отсутствие неожиданного full table scan на realistic fixture;
  • использование ожидаемого composite index;
  • отсутствие filesort/temp table там, где это критично;
  • одинаковую корректность на MySQL 8 и 9.

W5-03. Query budgets

Работы:

  • измерить фактические counts на realistic fixtures;
  • сузить слишком щедрые budgets;
  • добавить budgets для messages, forum, staff dashboard и API list endpoints;
  • отдельно учитывать lazy-loading violations;
  • сохранять диагностический список queries при превышении budget.

W5-04. Tracker load test

Сценарии:

  • invalid passkey flood;
  • valid steady announce load;
  • many peers for one torrent;
  • many torrents for one user;
  • repeated early announce;
  • scrape with multiple info hashes;
  • Redis degradation;
  • DB deadlock/retry.

Метрики:

  • requests/sec;
  • p50/p95/p99 latency;
  • DB queries/request;
  • Redis operations/request;
  • error/rejection rate;
  • CPU/memory;
  • lock contention.

Результаты фиксировать как versioned benchmark artifact, а не как жёсткое требование к конкретному developer machine.

10. Волна 6 — observability

P2
Цель

сделать metrics и health расширяемыми, безопасными и дешёвыми.

W6-01. Декомпозиция MetricsController

Выделить collectors:

  • HttpMetricsCollector;
  • DatabaseMetricsCollector;
  • RedisMetricsCollector;
  • CacheMetricsCollector;
  • SchedulerMetricsCollector;
  • QueueMetricsCollector;
  • TrackerMetricsCollector;
  • SearchMetricsCollector;
  • OutboxMetricsCollector.

Добавить:

  • общий MetricsCollector contract;
  • PrometheusFormatter;
  • unit tests каждого collector;
  • timeout/error isolation;
  • budget на latency и число DB/Redis operations самого /metrics.

Критерий приёмки

controller только оркестрирует collectors и формирует HTTP response.

W6-02. Исправить семантику метрик

Работы:

  • проверить, включён ли query log для nexus_db_query_count; если нет — собирать count через listener/middleware;
  • проверить корректность Horizon queue keys;
  • исключить неограниченную cardinality labels;
  • добавить process/runtime version labels без секретов;
  • документировать reset/persistence semantics Redis counters;
  • согласовать histogram buckets с фактической latency.

W6-03. Разделить liveness/readiness/diagnostics

  • /health/live: только способность процесса ответить.
  • /health/ready: только зависимости, без которых instance не должен получать traffic.
  • authenticated diagnostics: подробности MeiliSearch, Horizon, scheduler и outbox.

Решить и задокументировать:

  • является ли отсутствие queue worker readiness failure;
  • является ли отсутствие scheduler readiness failure;
  • допустим ли SQL fallback при отказе MeiliSearch;
  • какие timeout используются для каждого probe.

Не возвращать публично exception messages, hostnames или внутренние endpoints. Подробности писать в structured logs/Sentry.

W6-04. Защита /metrics

Работы:

  • в production требовать bearer token независимо от private source IP;
  • проверить trusted proxy configuration;
  • не доверять произвольному X-Forwarded-For;
  • поддержать token rotation;
  • добавить rate limit и access log без записи самого token;
  • добавить tests для IPv4, IPv6, proxy и неверного token.

12. Волна 8 — production readiness и delivery

P1–P2
Цель

доказать, что production artifacts запускаются с нуля и могут безопасно обновляться.

W8-01. Exact production Compose smoke test

В CI собирать production image и запускать:

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --wait

Тестировать на новых named volumes:

  • PHP health;
  • OpenResty config;
  • Vite assets и manifest;
  • static files из public/build;
  • writable storage/cache/attachments/torrents;
  • read-only rootfs;
  • non-root UID;
  • queue worker;
  • scheduler heartbeat;
  • DB/Redis/MeiliSearch connectivity;
  • route/config/view caches.

Отдельно подтвердить механизм заполнения public-build volume. Если он не нужен, удалить volume и обслуживать assets напрямую из immutable artifact. Если нужен — добавить явный init/copy step.

W8-02. Migration strategy

Работы:

  • разделить backward-compatible expand и contract migrations;
  • запрещать длительные blocking schema changes без отдельного плана;
  • измерять migration duration на production-like dataset;
  • перед destructive migration требовать backup verification;
  • документировать rollback и application compatibility window;
  • проверять миграции с предыдущего release, а не только migrate:fresh.

W8-03. Backup/restore verification

Автоматизировать test restore:

  • MySQL dump/restore;
  • Redis data, если оно содержит незаменимое состояние;
  • torrent files;
  • attachments;
  • required encryption keys/config references.

Критерий приёмки

восстановленный environment проходит critical smoke tests и содержит ожидаемые checksums/counts.

W8-04. Graceful deployment

Проверить:

  • queue restart без потери jobs;
  • scheduler singleton/overlap behavior;
  • Horizon termination;
  • FPM/OpenResty graceful reload;
  • cache warming;
  • readiness до включения traffic;
  • rollback на предыдущий image при совместимой schema.

W8-05. Supply-chain hardening

Работы:

  • pin GitHub Actions на immutable SHA;
  • не устанавливать инструменты без зафиксированной версии;
  • генерировать SBOM без изменения project dependencies во время CI;
  • подписывать конечные images digest, а не mutable tag;
  • прикреплять provenance/SBOM к тому же digest;
  • проверять signature перед deployment.

16. Метрики прогресса

Публиковать на каждый release или завершённую волну:

Quality

  • project и patch coverage;
  • mutation score critical modules;
  • число flaky/retried tests;
  • длительность CI по jobs;
  • количество fail-open steps.

Architecture

  • app() по namespace;
  • Globals/SupportContext references;
  • число shared GET/POST actions;
  • число oversized classes;
  • число public methods в top oversized classes;
  • legacy view baselines.

Security

  • открытые Critical/High findings;
  • возраст ignore entries;
  • endpoints без точной authorization matrix;
  • secrets/dependency scan status.

Performance

  • announce p95/p99;
  • torrent listing p95/p99;
  • queries per critical request;
  • queue depth/oldest job;
  • outbox pending/dead-letter/oldest age;
  • MeiliSearch indexing lag.

Operations

  • production cold-start success;
  • backup restore success date;
  • migration duration;
  • deployment rollback verification;
  • readiness failure rate.

18. Итоговые критерии завершения программы

Программа улучшений может считаться выполненной, когда:

  • обязательные CI/security/coverage проверки работают fail-closed;
  • каждый state-changing endpoint имеет отдельный HTTP action, validation и authorization;
  • critical application services не зависят от service locator или глобального request state;
  • announce/accounting выдерживает concurrency и cross-request isolation tests;
  • oversized classes существенно сокращены, а новый лимит не превышает 400 строк;
  • patch coverage и mutation score обязательны для critical modules;
  • inline handlers устранены, а legacy Blade baseline устойчиво снижается;
  • exact production Compose проходит cold-start test на пустых volumes;
  • migration, backup restore и rollback регулярно проверяются;
  • health, metrics и diagnostics имеют безопасные и однозначные semantics;
  • документация и ADR соответствуют фактическому состоянию проекта.
